# MaixCAM vision project checks

- Before changing the vision state machine, run `python -m unittest -v test_vision_rules` from this directory. Run it again after the change.
- If another editor or sync process restores old code and these tests fail, restore the agreed behavior in the implementation. Preserve unrelated user edits; do not reset the whole worktree or weaken the tests to make them pass.
- The shared 04/24/post-22 selector must check the confirmed X-distance threshold against every movable neighbor, use the red-specific limit when either object is red, accept a target with no neighbor inside its own X-distance threshold regardless of Y difference, and choose the qualified target whose center Y is nearest to the ROI center Y (absolute distance, not largest Y). DEBUG preview uses the same Y ranking. This applies to initial acquisition/reselection and RX14/RX44/post-22 decisions; a matched 04/24 lock is still followed without reranking.
- State 24 uses that selector only for initial selection or after losing its locked class. While that class is detected, associate the box nearest the previous position and keep tracking without X/Y jump or area-change rejection and without rerunning spacing, obstruction or maximum-Y ranking. Do not apply the generic jump-rejection stage to state 24. If no same-class detection remains, clear the lock and immediately rerun the merged selector. Seed the lock with the target that triggered TX24 after RX14/RX44 or RX22. New commands reset the lock; RXF1 preserves it until a fresh frame checks association. Once a black target is locked in 24, do not preempt it with a newly appearing red object.
- In state 24, send event 34 immediately when the selected target center enters the entire tracking ROI, then repeat every 500 ms while it remains inside. Do not require X/Y alignment with the ROI center. Stop repeating if the target leaves or is lost. Coordinate reference and below-ROI-center Y-error clamping remain unchanged.
- During MCU command 04, transmit errors relative to the image center. Send event 14 when X is within 20 pixels and the target center Y is no more than 20 pixels above the image center; passing below the center is allowed. After event 14, the wait-for-MCU-14 phase continues to use the ROI center.
- Exception for the first green task (green label before the first near-05 decision): initial/reacquisition in 03 and 04 chooses the verified green box with the smallest squared XY distance to the image center, without merged spacing/front-obstruction or generic position/area jump gates. Do not bypass verification or safety-zone exclusion. Continue inheriting and associating the 04 lock; five missing frames confirm loss. State 24 and pre-24 RX14/RX44/post-22 decisions still use the unchanged merged rules. Red and later tasks are unchanged.
- When 03 emits 04, seed the 04 lock with that selected target. Preserve and associate it through the wait-for-04 phase and MCU RX04 without re-screening; waiting for 04 and active 04 both publish image-center errors. Reset on other new commands. State 04 still uses merged screening if no inherited lock exists or after confirmed loss. Associate the nearest same-class box without X/Y jump, area-change, spacing or obstruction rejection. Retain identity for the first four missing fresh frames, send no stale coordinates, and confirm loss/re-screen at five consecutive missing frames. State 24 remains immediate-loss/reselection. Preserve the 04 lock across TX14 while waiting for RX14, with ROI-center errors there. The initial 03, arrangement and post-22 screening rules are unchanged.
- After MCU command 22, keep checking with that shared selector. Emit event 24 when a target qualifies; otherwise emit E2 at the existing 500 ms interval.
- In active 04, send one E4 after five consecutive fresh frames have no target; do not repeat during uninterrupted loss. A fresh accepted target re-arms E4 for the next confirmed loss, so MCU can react to its second loss. Exception: first-green recovery still keeps E4 consumed and suppresses 14 until MCU44, even if fresh coordinates reappear. RX44 directly enters the same arrangement decision as RX14 without another center-tracking/14 handshake. Track logs must distinguish raw, verified and safety-zone-filtered target counts on initial and confirmed misses; do not bypass verification or transmit stale coordinates.
- After MCU command 14 or 44, evaluate the next fresh frame with the shared merged selector: a qualified target emits 24 once and enters final ROI tracking; no qualified target emits 02 once and waits for MCU12. Do not restore the old side-only decision or five-second timeout.
- DEBUG previews raw YOLO target detections, not just verification-approved objects, so a raw detected target is not hidden by color/temporal verification. It must show every raw movable detection inside the candidate's applicable X threshold in white. A lone target outside safety zones with no other raw movable box is yellow immediately, even on first detection, after a missed frame or after a position jump. Only multi-object choices require the existing three-frame clear confirmation. This is visualization-only: yellow shows raw spacing-preview eligibility, not UART verification/coordinate transmission. Do not change UART acquisition or verification rules, and do not invent boxes for frames with no YOLO detection.
- DEBUG outlines the actual 06/16 obstacle-center trapezoid with four red lines in every UART mode; keep the ROI border. UART decisions and DEBUG must share zone_obstacle_region.py geometry. For 576x448 and the standard ROI, vertices are (238,100), (338,100), (575,379), (0,379): front edge centered on the image midline, 100px apart at Y=100; rear edge retains the ROI width and top+20 Y. Movable centers on any edge or inside qualify; outside centers do not. Retain accumulated-three-hit/36 handshake rules.
- DEBUG draws every current raw YOLO box in thin green with 4px outer padding, including non-target and safety-zone classes, independently of verification and screening. Keep screening yellow/purple/white borders inside, and clip green borders to the image. No additional text or changes to normal-mode/UART rules.
- Default UART coordinate publishing is on-new-frame (UART_SEND_RATE_HZ=0), not capped at 20 Hz. Submit wakes the UART worker immediately; its idle RX/timer poll is 1 ms. Send each submitted frame at most once, even for unchanged coordinates, using a frame sequence rather than timestamps. Keep only the newest pending coordinates, retain event priority and the existing 500 ms repeat/handshake rules. Keep 50 ms between queued command events for the MCU's single event slot; this must not limit ordinary coordinate frames. No MCU edits are permitted.
- Detailed diagnostics are enabled independently of the screen DEBUG button. Correlate raw detections, per-object verifier status/evidence, safety-zone exclusions, applied vs informational spacing/obstruction checks, selected/locked target, pending handshakes, and actual successful UART writes using monotonic milliseconds and frame sequence. Log changes and loss-confirmation boundaries immediately; sample stable frames/coordinates at 500 ms. Diagnostics must not affect selection/verification/protocol or synthesize coordinates. Report truncation explicitly. Package vision_diagnostics.py and keep tests covering logger-enabled equivalence and write success/failure.
- Latest tracking override: 03 locks its first selected target as well, including command51 black/green mixed search. Initial acquisition keeps the existing class verification and selection rules; once locked, 03/04/wait04/wait14/24 associate the nearest previous-center same-class box from the current raw YOLO detections, not the verifier's capped/color-checked subset. Do not rerun merged spacing, front obstruction, generic jump/area checks or color/temporal verification during association. Safety-zone exclusion still applies. Never publish cached/predicted boxes on a raw miss. 03/04 retain identity for four misses and release after five fresh missed frames; 24 keeps its existing immediate-loss/reselection behavior. Preserve the search lock for RX13; new target/search commands reset it. TX04 transfers the associated search target into the existing 04 lock. DEBUG remains a per-frame preview and does not change UART locking. This overrides earlier verification requirements only for already acquired locks, not initial selection or RX14/44/22 decisions.
- Never bulk-delete files or directories. Delete an individual file only by its explicit path.
